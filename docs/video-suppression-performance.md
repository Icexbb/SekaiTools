# 压制性能与编码并行度

压制管线为 VSPipe 解码、色彩转换和 VSFilterMod 字幕渲染 → 标准管道 → FFmpeg/x264 编码。VapourSynth 与 x264 原本已有自动多线程；单个字幕滤镜、编码依赖、内存带宽和磁盘都可能限制吞吐量。评估优化应比较相同输入、CRF 和速度档位的耗时/FPS，不能仅比较 CPU 占用率。

## 线程选择

- 任务设置中的“编码线程数”默认 0，表示由程序自动选择。
- 低于 1440 行的视频保持 x264 自动线程选择，避免小画面过多线程造成额外开销。
- 1440 行及以上自动选择 `min(逻辑处理器数 × 2, 高度 / 32, 128)` 帧编码线程；单逻辑处理器仍使用 x264 自动选择。高度限制控制短画面上的并行度，128 与 x264 的线程上限一致。
- 可手动设置 1–128，手动值优先。增加线程会增加编码内存及帧延迟，并可能改变码流和文件大小；保留相同 CRF、编码速度预设和字幕渲染器。字幕供帧不足时增加编码线程不保证提速。
- 从选视频时已有的元信息读取高度；非 GUI 调用未提供元信息时由压制层读取。日志显示本次选择的编码线程数。

## 本地对照

2026-10-05，16 逻辑处理器，VSPipe R70，同一 3840×2160/60 FPS 的 360 帧合成视频，无字幕，x264 medium/CRF 21，保留现有双输入/音频映射，交替运行各三次。x264 自动线程中位耗时 6.877 秒；32 线程中位耗时 6.396 秒，耗时约减少 7%，编码进程平均 CPU 占用由约 54–57% 增至约 59–61%。结果仅代表该短合成样例，不能外推为所有视频或字幕任务的收益。

1080p 同类样例未显示稳定收益，因此保持原自动策略。命名管道、大块双缓冲、显式 FFmpeg 输入队列也未显示稳定收益，未采用这些调整。没有替换 VSFilterMod，现有 ASS 特效及外部压制脚本继续使用。

## 退出与取消

监测每个进程的退出码。任一端异常退出或帧传输失败会停止另一端，避免 FFmpeg 退出后 VSPipe 阻塞在满管道上。外部取消也立即停止两个进程，等待管线结束，再清理临时输出；仅两端成功时提交输出文件。
