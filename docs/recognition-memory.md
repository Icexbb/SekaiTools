# 字幕识别内存优化

## 主要占用与处理

- 原文字模板按 5 倍字号绘制，再缩小成灰度/透明度匹配模板。原先匹配模板缓存还间接填充了原彩色模板缓存，每段不同文字都会保留大型原图。现在识别只缓存缩小后的匹配模板，临时彩色图在转换完成后释放。Marker 的特殊缩放也使用临时源图；导出姓名标签宽度复用匹配模板。
- 文字图裁剪原先返回共享大画布的 ROI，即使显示区域很小也保留整个底层分配。现在返回独立紧凑图像，释放画布。公开 `GetTemplate` 的缓存和借用语义保留；新增 `CreateTemplate` 返回由调用方释放的非缓存图像。
- Skia 转 OpenCV 原先将全部像素复制到托管 `byte[]`，再复制到原生 Mat。现在通过带行跨度的临时 Mat 视图直接复制原生像素，避免大对象堆数组，同时确保结果不依赖 Skia 位图的生命周期。
- 实时预览按原比例缩至 960×540 内，不放大小视频。4K BGR 单帧从约 23.7 MiB 降至约 1.48 MiB；容量 1 的队列和消费者临时帧均受益。识别/前一帧回查继续使用完整视频帧，匹配区域、阈值和缩放策略不变。
- GUI 空白预览改为一次创建的冻结 BitmapSource，读取绑定属性及重置时复用，避免每次读取都新建未及时释放的 Mat。

## 对照验证

2026-10-05，本机 1920×1080 模板设置、实际 FOT-RodinNTLGPro 字体，分别在独立进程中使用修改前/后的 TemplateManager。预热字体和原生库后，各生成并缓存 80 个不同的对话文本（`字幕识别内存测试000` 至 `079`），测量强制回收托管垃圾后的进程私有内存增量及期间的托管分配：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 私有内存增量 | 629.19 MiB | 6.36 MiB |
| 托管分配总量 | 620.85 MiB | 0.15 MiB |
| 本次生成耗时（含最终回收） | 0.90 秒 | 0.64 秒 |

以上是模板生成与缓存的局部测试，不代表完整识别任务内存会降低相同比例。解码器、全分辨率当前/上一帧、缩小后的模板及识别结果仍会占用内存；匹配模板缓存仍随不同文本增长。

对旧版实现逐像素比对四种模板用途的灰度和 Alpha，全部一致。新增测试覆盖预览边界、纵向视频比例、源帧独立性，以及文字模板裁剪和匹配层像素一致性。GUI 验证空白图在重复读取和重置时复用。

## 重置后内存高于首次任务前

总内存与托管堆不是同一指标。第一次解码、匹配、字体绘制及 WPF 渲染会初始化原生库和运行环境；Dispose 释放任务资源不意味着操作系统统计会回到尚未初始化时的值。判断残留应观察热身后的连续任务、旧对象是否可回收，以及解码器句柄是否释放。

重置现在异步等待识别线程、结束回调和后台进度保存完成，再释放处理器、清空列表/图片/时间线，并关闭独立播放窗口。界面完成清空后在后台执行一次完整回收及终结器等待（两轮回收处理可终结对象）；只发生在用户明确重置时，不用于逐帧处理，也不强制裁剪进程工作集。回收期间禁止启动新任务。旧处理器的局部引用在回收前移除。

识别主帧使用作用域释放；即使进度回调或持久化异常提前退出，也在工作任务 finally 中释放解码器，避免依赖以后才发生的原生终结器清理。

本机重复验证结果：

- 核心层同一 1080p/600 帧视频，运行至视频末尾并释放四次。每轮回收后旧处理器弱引用均失效；私有内存分别约 112.4、111.9、112.5、112.8 MiB，托管堆约 0.5–0.6 MiB。首次初始化前私有内存约 7.9 MiB，说明不能把冷启动值直接作为释放后的目标。
- WPF 使用真实重置路径连续四次，识别中取消，附带 4K 预览及列表项。旧处理器、4K 图片、列表项弱引用均失效，独立播放窗口确实关闭；私有内存约 229.8、229.8、229.9、230.4 MiB，托管堆约 7 MiB。该小样例未显示随任务轮次累积的占用，不代表已排除所有用户素材上的残留。
- 新增真实视频生命周期测试，验证停止操作会等待工作线程和结束回调，以及回调异常后解码器的原生指针归零。

## 使用内存提高识别吞吐（第一阶段）

设置页提供节省内存、自动、高性能三档，新建任务及恢复任务读取当前设置。默认自动；高性能缓存预算可设为 128–4096 MiB，默认 2048 MiB。旧设置文件缺少字段时保持自动模式。

| 模式 | 新增缓存预算上限 | 帧池容量上限 |
| --- | ---: | ---: |
| 节省内存 | 128 MiB | 4 |
| 自动 | 512 MiB | 16 |
| 高性能 | 用户设置 | 32 |

任务启动时按 Windows 实际可用物理内存的四分之一进一步限制预算，先预留 64 MiB 给复用的匹配缓冲，再用视频宽×高×3 计算帧池容量。容不下两帧时回退串行读取。预算针对新增缓存，不代表整个进程的内存上限，也不提前分配全部预算。当前阶段在任务启动时确定容量，尚未实现运行中根据系统内存压力调整容量。

单独的解码任务独占 VideoCapture，按顺序把帧、帧序号和原始时间戳交给识别线程。帧池包含正在识别的帧，不会另行无限追加；池满时解码等待，不丢识别帧。取消、正常结束及异常退出先停止并等待解码任务，再清空帧池、关闭解码器。断点保存使用已消费的帧序号，避免跳过预读但尚未识别的帧。

当前/上一帧上下文复用缩放 ROI 及粗匹配、精匹配结果缓冲；每次换帧仍重新计算像素。每个上下文的常规 ROI 缓存最多 16 个、16 MiB，两个结果缓冲分别最多保留 8 MiB，过大的匹配结果仍临时分配释放。模板匹配阈值、缩放方式、状态机推进顺序和预览分辨率保持原逻辑。模板提前生成和并行预处理留待后续针对完整剧情的测量。

2026-10-05，本机合成 1080p/600 帧视频，以空剧本运行至视频末尾，主要覆盖解码及内容起点匹配；串行和预读各预热一次，再交替测量三轮。串行平均 3479.0 ms，自动模式 16 帧预读平均 2449.6 ms，耗时缩短约 29.6%，吞吐提高约 42.0%。采样峰值私有内存约从 254–256 MiB 增至 343–347 MiB。两种路径的完整处理状态（包括时间戳）一致。此样例不是完整字幕剧情，不能将该提速比例直接套用到用户视频。

验证覆盖串行/预读的逐像素一致性、帧序号、时间戳、从指定帧定位后预读、视频末尾、队列满时取消、原生帧释放和取消后的断点位置。GUI 验证三档绑定、预算序列化、旧设置默认值，并复测连续四轮重置。并行阶段耗时会重叠，最终平均每帧耗时使用实际任务时间计算，阶段耗时仍单独记录。
