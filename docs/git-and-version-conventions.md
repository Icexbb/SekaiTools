# Git 提交与版本发布规范（跨项目模板）

本文提炼自本项目 `CLAUDE.md` 的 Git 提交和版本发布规范，可复制到其他项目的 `CONTRIBUTING.md`、`AGENTS.md` 或 `CLAUDE.md`。以书面规范为准，历史提交中的不一致写法不作为规则。

## 1. 项目适配项

应用前确定以下配置，并在项目文档中记录：

| 配置项 | 约定 |
| --- | --- |
| 版本来源 | 指定唯一维护入口，如版本文件、包清单或构建配置；其他版本字段与其同步 |
| 版本格式 | 选择三段式 `MAJOR.MINOR.PATCH`，或沿用本项目的四段式 `MAJOR.MINOR.PATCH.MMdd` |
| 发布说明目录 | 默认 `release-notes/`，每个版本单独一个 Markdown 文件 |
| 标签格式 | 默认与完整版本号完全一致，不添加 `v` 前缀 |
| 发布验证 | 指定项目的 Release／生产构建命令和完整测试命令 |
| 日期时区 | 使用日期后缀时，明确发布日期所采用的时区 |

本项目的具体配置是：在 `SekaiToolsGUI/AssemblyInfo.cs` 同步维护 `AssemblyVersion` 和 `AssemblyFileVersion`，采用四段式版本号。迁移到其他技术栈时替换路径和字段，不必保留程序集结构。

## 2. Git 提交规范

提交信息遵循 Conventional Commits 格式：

```text
<type>[(<scope>)][!]: <中文描述>

[可选正文：变更原因、影响及必要说明]

[可选页脚]
```

方括号表示可选部分，不写入实际提交信息。

- `type` 使用小写英文，按变更目的选择。
- `scope` 可选，使用简短的小写英文标识模块或影响范围；各项目自行定义并保持一致。
- 冒号后保留一个空格，描述必须使用中文，简洁说明完成的变更。
- 破坏性变更必须在类型或作用域后添加 `!`，并在正文或页脚说明影响；建议同时写清迁移方法。

| 类型 | 用途 |
| --- | --- |
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档变更 |
| `refactor` | 代码重构 |
| `perf` | 性能优化 |
| `test` | 测试变更 |
| `build` | 构建系统或依赖配置变更 |
| `ci` | 持续集成流程变更 |
| `chore` | 维护工作、版本发布等 |
| `revert` | 回退已有变更 |

示例：

```text
feat(search): 增加搜索结果筛选功能
fix(auth): 修复登录状态过期后无法重新登录的问题
docs(git): 补充提交信息规范
perf(cache): 减少重复读取配置的开销
refactor(config)!: 调整配置文件结构

BREAKING CHANGE: 移除旧版 server 字段，现有配置需迁移至 endpoints 字段。
```

## 3. 版本号规范

前三段按语义化版本递增，根据本次最终交付变化中影响最大的类别决定：

| 变化 | 递增规则 | 示例 |
| --- | --- | --- |
| 不兼容的破坏性变更 | 主版本加一，次版本和补丁归零 | `1.4.2` → `2.0.0` |
| 向后兼容的新增功能 | 次版本加一，补丁归零 | `1.4.2` → `1.5.0` |
| 向后兼容的缺陷修复 | 补丁加一 | `1.4.2` → `1.4.3` |

不能只根据提交类型机械决定版本。例如，带破坏性影响的 `refactor` 也需要按不兼容变更处理；工程和依赖调整应按实际交付影响判断。

本项目附加的 `.MMdd` 表示发布日的两位月份和日期，例如 `1.5.0.0911`。这是项目自定义的四段式版本格式，**不是严格的 SemVer 格式**。其他项目应根据包管理器和发布平台的要求选择三段式或四段式。

为保证跨项目使用时版本唯一且可排序，补充以下约束：日期后缀不能替代前三段递增；同日再次发布也必须产生新的版本号，不能复用已发布版本。跨年时同样不能只依赖 `MMdd` 判断新旧。

所有表示同一发布版本的字段、发布说明文件名及标签必须一致。若技术平台要求不同格式，应在项目中明确转换规则。

## 4. 发布说明规范

每个版本必须新增 `release-notes/<版本号>.md`，使用“主要更新”结构，按实际内容选择“新增、优化、修复、工程、测试”等分类。没有内容的分类直接省略。

- 以最近的适用版本标签到待发布提交的提交记录为线索，汇总重要变化。
- 必须结合该范围的最终 `git diff` 核对实际交付内容。
- 只描述相对上一版本的最终净变化，排除已回退、被替代、开发过程中短暂存在或未进入交付物的改动。
- 同一功能多次修改只写最终保留的行为；最终状态与上一版本一致则不记录。
- 面向用户和维护者说明新增能力、体验改善、问题修复及重要工程变化，不机械复制提交信息，不罗列无关实现细节。
- 不遗漏用户可感知的重要变化；存在破坏性变更时说明影响和迁移方法。

模板：

```markdown
## 主要更新

### 新增

- 支持按状态筛选记录，便于快速查找待处理事项。

### 优化

- 减少重复加载，提高列表打开速度。

### 修复

- 修复登录过期后无法重新登录的问题。

### 工程

- 更新运行时依赖，并适配相关接口。

### 测试

- 增加登录过期和重新登录场景的测试覆盖。
```

## 5. 发布流程

1. 确定发布基线：选择当前发布线的最近版本标签，检查它到 `HEAD` 的提交记录与最终差异。首次发布没有标签时，以本次完整交付内容为依据。
2. 根据最终变化决定新版本号，同步修改所有相关版本字段。
3. 新增对应发布说明，核对内容是否准确反映最终交付状态。
4. 完成项目规定的 Release／生产构建和完整测试；失败时先修复，不能继续创建发布标签。
5. 将版本号和发布说明纳入同一个发布提交，使用固定格式：

   ```text
   chore(release): 提升版本至 <版本号>
   ```

6. 复核发布提交：确认包含正确的版本号和发布说明，并再次核对相对基线的最终差异。如果验证后又修改了代码或构建输入，必须重新执行受影响的验证。
7. 创建与完整版本号同名的标签，指向该发布提交；按项目既定流程推送并发布。

辅助检查命令（尖括号内容需替换，不可原样执行）：

```text
git log <上一版本标签>..HEAD --oneline
git diff <上一版本标签> HEAD
git show <发布提交> --stat
git diff <上一版本标签> <发布提交>
```

## 6. 发布约束

- 不允许只提升版本或只创建标签而缺少发布说明。
- 不允许在 Release／生产构建或完整测试未通过时创建发布标签。
- 标签必须指向包含对应版本号和发布说明的发布提交。
- 已推送标签如需改写，必须先获得用户明确确认。

原项目未规定分支命名、合并策略、预发布版本和提交自动校验机制；这些内容由目标项目另行约定。
