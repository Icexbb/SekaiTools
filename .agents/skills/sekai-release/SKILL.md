# SekaiTools 版本发布

仅执行用户请求的发布范围。请求整理发布说明或准备版本时，完成相应产物；不要据此推送、上传或创建远程 Release。完整发布请求中的本地版本提交和新标签可按下述流程执行；远程发布依照用户已授权的目标和仓库现有机制执行。

## 项目依据

从本文件所在目录向上三级定位仓库根目录，所有命令在该根目录运行。先阅读 [CLAUDE.md](../../../CLAUDE.md) 和 [Git 提交与版本发布规范](../../../Docs/git-and-version-conventions.md)，后者是版本和发布说明的维护来源。若规则已更新，以当前仓库规范为准。

- 版本维护入口：[SekaiToolsGUI/AssemblyInfo.cs](../../../SekaiToolsGUI/AssemblyInfo.cs) 中的 `AssemblyVersion` 和 `AssemblyFileVersion`，必须相同。
- 版本格式：`MAJOR.MINOR.PATCH.MMdd`，日期使用 Asia/Hong_Kong 的发布日；不要固定为本 skill 创建日期。
- 同步检查 [build.bat](../../../build.bat) 的 `VERSION`，以及实际参与打包、上传的其他版本字段。Updater 的独立程序集版本不自动跟随主程序递增。
- 发布说明：`release-notes/<完整版本号>.md`。
- 标签：完整版本号，不加 `v`，指向包含版本号和发布说明的发布提交。

## 确定基线与版本

1. 检查 `git status --short`、当前分支、现有标签和提交。保留用户改动，不把未完成或无关改动混入发布；存在影响本次产物的未提交改动时先明确其归属。
2. 在当前发布线中选择最近适用且属于当前提交祖先的版本标签，不机械采用日期最新或版本最高的其他分支标签。可用 `git tag --merged HEAD --sort=-version:refname` 辅助查找，并与版本文件及发布说明核对。
3. 阅读基线到目标提交的 `git log` 和最终 `git diff`；首次发布无标签时检查全部待交付内容。以净变化决定前三段：不兼容变更升主版本，兼容新增能力升次版本，兼容修复升补丁。工程调整按交付影响判断，不能只按提交类型判断。
4. 用户指定版本时检查格式、递增及标签冲突。同日再次发布仍需递增前三段，日期后缀不能替代递增。不得覆盖已有发布说明或复用已发布版本。

## 准备发布内容

同步版本字段，新建对应发布说明。使用“主要更新”结构，按实际内容选择“新增、优化、修复、工程、测试”，省略空分类。根据最终差异描述用户可感知的结果，排除回退、被替代和未交付内容；破坏性变更说明影响及迁移方法。模板和详细规则见规范文档，不机械复制提交记录。

## 验证发布产物

执行 Release 构建、完整测试及 GUI 发布：

```powershell
dotnet build SekaiTools.sln -c Release
dotnet test SekaiTools.sln -c Release
dotnet publish SekaiToolsGUI/SekaiToolsGUI.csproj -c Release -o Build/
```

直接发布命令优于盲目运行 `build.bat`，该脚本含清理 Build 目录的操作。选择其他输出目录时保持路径位于当前工作区。

检查当前 GUI 项目发布目标及产物：`BuildUpdater` 应生成并复制 `Updater.exe` 和 `7zr.exe`，`OrganizeOutput` 应整理 `libs/`；核对主程序、运行所需文件、`network-endpoints.json` 及产物中的主程序版本。不要仅凭命令启动或目录存在断言发布成功。需要启动程序验证时避免覆盖用户数据或执行真实更新。

任何构建、测试或发布失败均先处理失败，未通过前停止创建发布标签。验证后修改代码或构建输入，重新执行受影响验证。测试宿主连接超时属于运行环境问题，应明确区别于测试断言失败；不得将未执行的测试报告为通过。

## 提交与标签

1. 复核版本字段、发布说明文件名及最终差异，只暂存本次发布文件。按 CLAUDE.md 自动提交，无需重复询问已授权的本地提交：

   ```text
   chore(release): 提升版本至 <完整版本号>
   ```

2. 用 `git show <发布提交> --stat` 及 `git diff <基线标签> <发布提交>` 确认提交包含版本和说明，且对应已验证的产物。
3. 完整发布范围内创建同名新标签并核对指向；准备版本或仅写发布说明时不自行扩大到标签和远程发布。已存在标签先检查，不能强制覆盖；改写已推送标签必须有用户明确确认。
4. 远程推送、创建 Release、上传安装包应使用仓库当前发布机制和用户授权的目标。没有明确远程目标时完成本地工作并说明剩余项，不凭历史命令猜测服务、资产格式或上传地址。

## 交付报告

简要列出版本、基线、发布说明路径、验证结果、产物目录、发布提交和实际创建的标签。只有执行并确认成功的推送或远程 Release 才提供对应完成状态和链接；仍有失败或待授权步骤时明确说明。
